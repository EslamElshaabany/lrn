The node, and the patterns that solve 90% of these problems
Every linked list problem is a recombination of a few pointer moves. Learn these four and most "hard" list problems become bookkeeping.
class ListNode {
    int val;
    ListNode next;
    ListNode(int val) { this.val = val; }
}

1 — Dummy head node

Avoids special-casing "what if the head changes." If the head might change or get removed, add a dummy — don't reason about whether this specific case needs one. It costs nothing and eliminates a whole bug category.
ListNode dummy = new ListNode(0);
dummy.next = head;
// ... do stuff, walk a tail pointer ...
return dummy.next;

2 — Fast / slow pointers

Find the middle, detect cycles, find nth-from-end. slow moves one step, fast two. When fast falls off the end, slow sits at the middle.
ListNode slow = head, fast = head;
while (fast != null && fast.next != null) {
    slow = slow.next;
    fast = fast.next.next;
}
// slow is now at the middle

3 — Iterative reversal (three pointers in lockstep)

public ListNode reverseList(ListNode head) {
    ListNode prev = null, curr = head;
    while (curr != null) {
        ListNode next = curr.next;  // save before overwriting
        curr.next = prev;           // reverse the link
        prev = curr;                // advance prev
        curr = next;                // advance curr
    }
    return prev; // prev ends up as the new head
}
Order matters: save next before overwriting curr.next, or you lose the rest of the list.
Why prev is needed at all: reversing a link means pointing curr.next backward. To do that you need a live reference to the node before curr — that's prev. In a singly linked list, once you move past a node there's no way back. prev starts at null because the original head becomes the new tail, and a tail's next is null.
Cycle detection — Floyd's tortoise & hare
slow moves 1, fast moves 2. If there's a cycle, fast laps slow and they collide. If there isn't, fast walks off the end.
public boolean hasCycle(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) return true;
    }
    return false;
}

Interactive — watch the hare lap the tortoise

Press step. The last node loops back — fast will catch slow inside the cycle.
Why they're guaranteed to meet: once both are inside the cycle, fast gains exactly 1 node on slow each step. The gap shrinks by exactly 1 — it can't skip over 0. A gap of 1 always becomes 0 next step. Meeting is arithmetic, not luck.
Three details that bite: check fast != null && fast.next != null before fast.next.next (NPE guard). Compare after both move. Use ==, not .equals() — == says what you mean: "same node in memory."
Where in the list you meet varies (but it's always O(n))
Steps to meet ≈ μ + λ — μ (tail length, head → cycle start) plus λ (cycle length).
ShapeTime to meet
Self-loop (λ=1)Fastest — within 1 step of entering
Short tail, short cycleVery fast
Long tail, small cycleMost time just reaching the cycle
Tiny tail, huge cycle (λ≈n)Slowest — close to n steps
Finding the cycle's start: after they meet, reset one pointer to head. Move both one step at a time — they meet again exactly at the cycle's entry point. Same μ/λ math.
Merge two sorted lists — two pointers + dummy
Walk both lists, always attach the smaller head to a growing tail. dummy.next is fixed the moment the first node attaches — the head is never lost, no matter how far tail walks.
public ListNode mergeTwoLists(ListNode l1, ListNode l2) {
    ListNode dummy = new ListNode(0), tail = dummy;
    while (l1 != null && l2 != null) {
        if (l1.val <= l2.val) { tail.next = l1; l1 = l1.next; }
        else                  { tail.next = l2; l2 = l2.next; }
        tail = tail.next;
    }
    tail.next = (l1 != null) ? l1 : l2;
    return dummy.next;
}

Bug this prevents: reusing one variable as both "the head" and "the thing that advances" (list3 = list3.next). Once it moves past the first node, nothing points at the start — you return the last node.
Comparison direction: if (l1.val > l2.val) picks the larger value. For ascending order you want <= — a one-character flip that's easy to miss.
Min-heap variant — earns its keep for k lists
Drive the loop off !heap.isEmpty(), not the list references — null lists just never get offered. For two lists, two-pointer is simpler and O(1) space vs. the heap's O(log n); the heap only pays off merging k lists.
PriorityQueue<ListNode> heap = new PriorityQueue<>((a, b) -> a.val - b.val);
if (l1 != null) heap.offer(l1);
if (l2 != null) heap.offer(l2);
ListNode dummy = new ListNode(0), tail = dummy;
while (!heap.isEmpty()) {
    ListNode node = heap.poll();
    tail.next = node; tail = tail.next;
    if (node.next != null) heap.offer(node.next); // node.next, never tail.next!
}
return dummy.next;
Heap traps: looping on l1!=null && l2!=null (never reassigned → infinite loop); forgetting tail = tail.next (overwrites one slot); re-offering tail.next instead of node.next (that is the node you just polled → duplicates / self-loop).
Removing nodes by value
The bug to recognize: if prev starts equal to head (no dummy) and the head needs removing, prev.next = curr.next is a no-op — prev is curr, and a node can't detach itself. The dummy makes prev and curr start on different nodes.
public ListNode removeElements(ListNode head, int val) {
    ListNode dummy = new ListNode(0, head);
    ListNode prev = dummy, curr = head;
    while (curr != null) {
        if (curr.val == val) prev.next = curr.next; // skip curr
        else                 prev = curr;            // only advance when kept
        curr = curr.next;
    }
    return dummy.next;
}

Interactive — dummy + prev/curr, remove all 6's

prev starts on the dummy, curr on the head. prev only advances when we keep a node.
Critical detail: prev advances only in the else branch. Advance it unconditionally and it can end up pointing at a node you just removed.
Recursive approach — trust the contract
removeElements(node, val) returns the head of the correctly-filtered list starting at node. Once you commit to that contract, you don't trace three nodes deep — you trust it.
public ListNode removeElements(ListNode head, int val) {
    if (head == null) return null;                 // empty stays empty
    head.next = removeElements(head.next, val);   // fix the rest first
    return head.val == val ? head.next : head;    // then decide about head
}
No dummy needed — every call returns its own correct head to its caller, so there's no broken link to reach backward and fix.
Trace of [1, 7, 2], removing 7: 
removeElements([1,7,2])
  head=1 → removeElements([7,2])
    head=7 → removeElements([2])
      head=2 → removeElements([]) → null
      2 != 7, keep → returns 2
    7 == 7, skip → returns 2        (7 discarded here)
  1 != 7, keep → returns 1
result: 1 -> 2
Node 7 needs no special handling for head-vs-middle — recursion doesn't know or care about position. That's the payoff.
Trade-off: O(n) time either way, but recursion is O(n) space (call stack) vs. O(1) for the iterative dummy version. On very long lists, recursion risks StackOverflowError where iteration wouldn't.
The "way of thinking" checklist
Run through this before writing any linked list code.
  1. Can the head change or get removed? If yes → dummy node, no exceptions.
  2. What has to move relative to what?
    single pointer → plain traversal · prev+curr → deletion/insertion (you always need the node before the one you change) · slow+fast → middle, cycle, nth-from-end · prev+curr+next → reversal.
  3. Does it decompose into "fix the rest, then handle this one node"? If so, recursion may be cleaner (reversal, merge, removal all fit). The hard part is trusting the contract instead of unfolding the whole stack.
  4. Trace 3 states on paper first: empty list · target is the first node · target is the last node (or absent). If pencil-and-paper breaks on any, the code will too.
  5. State your invariant as a sentence. e.g. "prev.next is always the last kept node's link, pointing at whatever curr is about to examine." If you can't say it out loud, that uncertainty becomes the bug.
  6. Advance pointers in a deliberate, fixed order. Order-of-operations mistakes are the #1 source of lost nodes.
Most "stuck" moments on simple problems aren't a syntax gap — they're step 4 getting skipped. Pencil-and-paper tracing catches these in ~10 seconds.

Common Java-specific bugs, quick reference

NPE from chaining .next.next without checking both aren't null first (fast != null && fast.next != null).
Forgetting to advance the tail when building a new list — reusing one variable as head-holder and tail-advancer loses the head.
== vs .equals() — for ListNode, .equals() happens to fall back to reference equality (not overridden), but == states the actual intent and doesn't depend on that holding.
Losing a reference during reversal by reordering the assignments, or overwriting curr.next before saving it to next.
Comparison direction in merges — <= vs > flips ascending/descending; a one-character slip.
Re-offering the wrong node to a heap — always push node.next, never tail.next (which right after linking is the node you just polled).
Looping on the wrong condition — with a heap or dummy pattern, drive the loop off the data structure's actual state (!heap.isEmpty(), curr != null), not variables that never get reassigned inside the loop.
